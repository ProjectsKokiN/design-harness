# 共有の規約 — iOS と Android の両方で成り立つと確かめたもの

**ここに置いてよいのは、両方の棚卸しで対応が確かめられた規約だけです。**
片方にしか無いものは、そのプラットフォームのスキルに置きます（`README.md` の判定規則）。

出どころは `analysis/merge-build-2026-09-06.{json,md}`。各規約に根拠の行 id が付いています。

```
python3 build/merge_check.py          # 根拠が生きているかを見る
python3 build/merge_check.py --stamp  # 指紋を押し直す（**人が確かめたあとに打つ**）
```

## 根拠は腐ります

**片方が行を直すと、引いた先が別の主張に変わっても気づけません。**
2026-09-06、Windows が Android 104（5つの主張を1行に束ねていた）を分割したとき、
**規約4と5 は根拠が抜けたまま残っていました**（文は 199 / 200 へ移り、104 は別の主張になった）。
id は消えず `none` のままだったので、実在の確認だけでは捕まりません。

いまは各規約が**根拠の行の `手順` の指紋**を持ち、中身が変わったら落とします。

## 書き足すときの決まり

1. **片方の棚卸しにしか根拠が無いものを書かない。** 両方の id を付けられないものは、まだここではない
   - **例外は共有の道具（`tools/`）の実害。** 3台とも回すものなので**片側の事実ではありません**。
     ただし**棚卸しの行ではないので id 欄には入れず**、`$ハーネス側の根拠` に分けて置きます
     （`merge_check` の指紋が当たらないため。2026-09-07 に規約22 でこの形を採りました）
2. **どちらかの言い回しをそのまま使わない。** iOS 固有の語・Android 固有の語を入れない
3. **薄めない。** 両方の必須条件が残っているかを確かめる
4. **工程で区切って突き合わせない。** 1回目にそれをやって、工程が食い違う組が出会えませんでした
5. **足したら `--stamp` を打つ。** ただし**赤を消すために打たない**（検査が空振りになります）

## 根拠の重みが違うものがあります
**Android 199 / 200 / 201 の実体は、iOS 側が書いた SESSION_LOG の写しです**（`2026-09-04 セッションログ（Mac mini / iOS ビルド）`）。つまり規約 4・5・21 は「2つのプラットフォームが独立に同じ結論へ達した」証拠ではなく、**1つの決定が3台共通として宣言されている**ことを根拠にしています（出典の節が自ら「3台の運用に関わる変更なので他マシンにも読んでいただきたい」と書いている）。共有層に置くこと自体は妥当ですが、**両側の独立した実践に支えられた規約とは重みが違います**

**2026-09-07 に規約15 を取り下げました。** 以前ここには「iOS 334 が2つの規約の根拠に
なっているのは意図」と書いていましたが、**不正確でした**。1行から2つ出ていたのではなく、
**片方（15）の文が iOS 側の根拠より広かった**のです（334 は「確認の記録」の話で、
「配布物の素性」を支えていません）。**iOS の配布に素性を残す記述は 0件**と実測したので、
Android だけの規約として取り下げ、334 は規約19 に一本化しました。
取り下げの記録はこのファイルの末尾にあります（**消しません**）。

## 1. ビルドコマンドに `--no-tree-shake-icons` を含めない（フラグ無しで release ビルドが通る状態を保つ）。この失敗の原因は実行時に IconData を組み立てているコード側にあり、恒久対応は IconData をすべて const にすること。フラグを暫定的に使ってよいかは iOS と Android で扱いが異なるため、共有層では定めない（各プラットフォームの規定に従う）。
**工程**: ビルド　**根拠**: iOS `[106, 107]` / Android `[36, 196, 75]`

<details><summary>反証の結論</summary>

反証を試みたが崩せなかったので keep。主張の一致を3点で確認した。(1) 標準のビルドコマンドにフラグを含めない：iOS 106「常用しない」／Android 36「付けない」（build_and_upload.ps1:9-13 に実体あり）・75「付けない」・196「有効のまま通る」。(2) 原因の特定：iOS 107「コード側の実行時 IconData 生成」／Android 36 の罠「動的生成をやめる方向で直す」。(3) 恒久対応：iOS 107「const 化」／Android 36「全て const にしたことで通る」・75「const にして不要になった」。さらに iOS 106 の罠と Android 196 が同じ実測値（MaterialIcons-Regular.otf 1,645,184→1,420 バイト）を挙げており、同一事象を指していることが確認できる。フラグは Flutter 共通のため、どちらのプラットフォームで実行しても意味のある動作になる（片方に不要な手順を配っていない）。

書き直した箇所は2つ。第一に、元の rule の「既定で付けない」を「ビルドコマンドに含めない」に変えた。「既定で」は例外的使用を許す含みを持つが、Android 36 は罠で「その場しのぎでフラグを戻さず」と暫定使用も明確に禁じている。このままだと Android 側の条件を薄める。第二に、その食い違い（iOS 107 は暫定使用を認める）を規約の外に明示して置いた。元の提案は evidence 欄で食い違いに触れつつ rule 本文では黙っていたため、読み手には「暫定は可」とも「一切不可」とも読めてしまう。逆に一律「付けない」と書けば iOS 107 の記述に反するので、共有層では定めないと明記する形にした。

残る留保（対応を壊すほどではないと判断）：Android 36 は「使う22定数が APK のフォントに残ることをファミリー別に照合済み」という Android 固有の照合に触れているが、これは一度きりの確認の記録であって継続手順ではないため規約に含めなかった。また iOS 107 の案件差に「PlantTalk は --no-tree-shake-icons を常用」、Android 36 の罠にユーザーのグローバル記憶が「必須」のままという指摘があり、未修正の案件が現存する。これは規約への反例ではなく未対応の個別事例だが、共有層に上げる際は人が確認したほうがよい。

</details>
