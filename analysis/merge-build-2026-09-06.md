# ビルドの棚卸しの突き合わせ（段2・2026-09-06）

入力は `build-ios-2026-09-06.json`（377行・Mac mini）と `build-android-2026-09-06.json`（198行・Windows）。
対象は `design-harness@fbed287`。

工程ごと（10段）に両方の `依存 = none` を突き合わせ、**対応が付いたものを別の主体が反証**した。
評価軸は3つだけ——**片方の必須条件を落としていないか**・**相手に不要な手順を配っていないか**・
**本当に同じ主張か**。迷ったら対応を付けない側に倒した。

## 2. 反証が落とした4件（嘘の共通規約になるところだった）

| 工程 | 対応 | なぜ落としたか |
|---|---|---|
| 取得 | iOS [84] × And [11] | 両者は「main に居ろ」と言っているだけで、守っている対象も関門の位置も違う… |
| 仮想機の確認 | iOS [221] × And [85, 125] | 3点で嘘の共通規約になります… |
| 報告 | iOS [371] × And [104] | iOS 371 は「対応表にする」と「書かれた項目には全部答える（漏らさない）」の2条件を持つが、Android 104 が言っているのは「見たこと（何を見て・どうだったか）を表で書く」だけで、依頼項目を全部埋めることは要求していない… |
| 報告 | iOS [358] × And [104] | iOS 358 は「何を見て何を見ていないかが分かる形にする」であり、罠に「見ていないものを黙って落とすと、読む人は見たと受け取る」と書かれている通り、守りたいのは『見ていない項目の明示』のほう… |

特に重いのは**報告の2件**です。iOS の「**何を見て、何を見ていないかが分かる形にする**」を
「何を見たか」に薄めると、**見ていない項目が黙って落ちます**（罠に「読む人は見たと受け取る」とある）。
Android 側に同じ条件が無いので、**条件を戻すと今度は Android に根拠のない規約を配る**ことになります。
だから共有層に置かず、両方に残しました。

## 3. 確定した共有の規約（12件）

`build/shared-rules.md` に置きました。ここには一覧だけ。

1. **[ビルド]** ビルドコマンドに `--no-tree-shake-icons` を含めない（フラグ無しで release ビルドが通る状態を保つ）。この失敗の原因は実行時に IconData を組み立てているコード側にあり、恒久対応は IconData をすべて const にすること。フラグを暫定的に使ってよいかは iOS と Android で扱いが異なるため、共有層では定めない（各プラットフォームの規定に従う）。
2. **[前提]** 必要な生成物（git 管理外の生成物を含む）が無いときは、後段の失敗に埋もれさせず、確認した時点で1行で止め、その生成コマンドをそのまま画面に出す。無いまま先の工程へ進めない
3. **[取得]** 確認・作業に入る前に `git pull --ff-only origin main` を実行し、main を origin の最新まで fast-forward で追いつかせる。fast-forward できない（分岐している）場合はマージせずそこで止める。
4. **[報告]** 確認するのは依頼に書かれた項目だけにし、確認項目を自分の判断で追加しない。
5. **[報告]** 試験が担保している項目は画面で確認せず、試験の結果（通過件数）として報告する。
6. **[報告]** 他のマシンが作った pull request は自分でマージしない（検証した環境が違うため）。
7. **[実機の確認]** 実機での見た目の合否は人が判断する。機械側の受け持ちは、成果物が端末に入って起動したことを確かめるところまでを上限とし、その先（見た目の合否）には踏み込まない。判定の結果を待って止まらない。
8. **[検品]** push の関門は、フックのパス設定（core.hooksPath）で案件内の .githooks を指し、その pre-push が案件の検査スクリプト design/verify.sh を「呼ぶ」形（検査を書き直して2か所に持たない）に配線する。push を通す条件は、その検査が通ること。
9. **[検品]** 1回の作業の中で、同じ検査コマンドを2回以上回さない（design/verify.sh を含む）。結果を確かめ直したいときも回し直さず、前回の出力を読み直す。
10. **[記録]** 作業の記録は、そのリポジトリ内の SESSION_LOG.md に書く。Notion など外部サービスには保存しない（2026-08-14 にこの形へ変更）
11. **[記録]** 記録は1か所に書く（2026-09-04 変更）。詳細は SESSION_LOG.md にだけ書き、他の置き場は要点だけ書いてログを指す。アーカイブ（MACHINE_TASKS_ARCHIVE.md）は結果の表と数行、PR 本文は結論2〜3行にとどめ、同じ内容を複数箇所へ書き写さない（表も書き写さない）
12. **[記録]** 確認時のスクリーンショットは git に入れない。build/ 配下のプラットフォームごとのディレクトリ（iOS: build/simulator-shots/、Android: build/emulator-shots/）に置き、記録にはそのパスだけを書く

どれも**両方の実体を読んで**確かめています。たとえば1件目（生成物が無ければ止める）は、
iOS が `simulator_check.py:73-75` で `Runner.app` の不在を見て `flutter build ios --simulator --debug` を出し、
Android が `verify.sh:29-33` で `build/content.db` の不在を見て `python3 scripts/build_db.py` を出す——
**対象もコマンドも違うが、主張が同じ**という形です。
