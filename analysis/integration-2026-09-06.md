# Mac mini × Windows 統合（2026-09-06）

2台が独立に行った「開発の仕組み化」の分析を突き合わせ、**統合するもの・機体ごとに分けるもの**を
決めた文書です。材料は次の2つ。

- Mac mini: 事例 79 件（この文書の作成者。反証3視点のうち2つが最初の仮説を退けた）
- Windows: 事例 78 件（`analysis/windows-mechanism-2026-09-06.md`。設計3案 → 審査 → 反証6件）

---

## 1. 結論

**主因は2つとも共通でした。** 独立に調べた2台が、同じ2つに行き着いています。

| 主因 | Mac mini | Windows | 判定 |
|---|---|---|---|
| 出した記録を**読む段が1つも無い** | `simulator_runs.json` を読む段 **0件** | `emulator_runs.json` を読む段 **0件**（唯一の読み手は書き手自身） | **共通の穴** |
| 学びを書き戻す経路に**自発の段が無い** | スキル9コミットの自発 **0件**。24日間で編集ゼロ（その間セッション118件） | きっかけは 失敗39 / ユーザー起点20 / **日常の自発2** | **共通** |

ただし**症状の出方が逆**です。ここが分離の線になります。

| | Mac mini | Windows |
|---|---|---|
| 専属スキル | `flutter-ios-build-check` **490行** | **無い** |
| 手順の置き場 | スキル | 案件の `scripts/`（機体の手順 17件中 **12件**） |
| 書き戻り先 | skill 20 / 部分13 / **未反映46（58%）** | harness 24 / script 23 / project-doc 18 / **skill 6（8%）** |
| 分類の偏り | 機体の手順 25 / 判断の規約 29 | 機体の手順 17 / **判断の規約 39** |

**Mac mini は「置き場はあるが届いていない」、Windows は「そもそも置き場が無い」。**
Windows の判断の規約が多いのは、手順が言語化されないぶん**判断の言葉としてだけ残っている**ためと読めます。

## 5. 唯一の論点 —「機体の手順」をどこに置くか

Windows は **「新スキルを作らない」**と判断しました。理由は「`~/.claude` は3台にしか同期されず、
他メンバーの clone に届かない」。一方 Mac mini は**スキルに置いて実際に機能**しています（490行）。
Windows 自身が「**2台の分析を統合するときの最初の論点**」と名指ししています。

### 判断（提案・確信度 中）

**両立します。分ける基準は「正本か、本人の段取りか」です。**

| | 置き場 | 中身 |
|---|---|---|
| 正本（他メンバーに届く必要がある） | 案件の `scripts/` ＋ 共有層 `design-harness` | 器・検査・配線 |
| 本人の3台の段取り | `~/.claude/skills/` | 「どの順で何をやるか」「誤誘導エラーの読み替え」 |

**Windows の「新スキルを作らない」は正本の話であって、手順を言語化しない理由にはなりません。**
実害が出ています——機体の手順17件が skill 0件・script 12件で**案件をまたげず**、両案件で42件が
繰り返し、Norton の7行は12ファイルに複製されました。

そこで Windows 側は**スキルを作らず**、「どの案件にも要る骨格」だけを
`design-harness/guides/windows.md`（`acceptance/windows.md` の隣）に置くことを提案します。
案件の `scripts/` が正本のままで、骨格だけが案件をまたぎます。

**覆る条件**: 他メンバーが実際に Android を触る予定が無いなら、Windows もスキルでよく、
この分離は過剰になります。
