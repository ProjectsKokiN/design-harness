## 論点2: トークンの実装率

### 先人がやっていること

- 共通の形: Figma プラグイン → JSON → Style Dictionary → Swift。**iOS 対応は最終段の
  テンプレート差し替え**として扱われる
- `.colorset/Contents.json` まで作るのは `RedMadRobot/figma-export` のみ。
  他（Style Dictionary の ios-swift、Supernova、design-extract）は Swift ソースへ直接書き出す

### 私の案

「宣言されたトークンのうち、いくつがコードにあるか」を数える段（`token_impl_check.py`）。

### 採るほうと理由

**私の案を捨てます。**

**数えるということは、手で書いたものを後から照合するということです。**先人は全員、数えずに
**生成しています。**生成すれば実装率は定義上 100% になり、既存の `gen_verify.py`

## 論点3: 見てもらう場（カタログ）

### 先人がやっていること

**`#Preview` を自動で集める方式が主流でした。**

| 仕組み | 集め方 |

一方、**デザインシステム系のカタログ（Microsoft Fluent・Skyscanner Backpack・Orange）は

### 採るほうと理由

**採るのは `#Preview` の自動収集です。**

**ただし穴が2つ残り、そこは我々のやり方で埋めます。**

1. **プレビュー自体を書き忘れる。** 調査では「カタログに載っていない＝作られていない、を

   **我々は分母を Figma の component set から取れます**（`impl_coverage_check` と同じ考え方）。
   **ここは先人が持っていないので、我々のものを残します**

## 論点4: 自己申告で工程が飛ぶ

### 先人がやっていること

**3つの型が繰り返し出てきました。**

1. **対象を人に選ばせず、機械に全列挙させる**（element-x はプレビューを総なめし、
   除外は名前で明示。SnapshotPreviews・Prefire も同じ）
2. **正解が無い・ずれた時点で必ず赤にし、正解の更新経路を別に閉じる。**
   `swift-snapshot-testing` は参照画像が無い初回は**必ず失敗**。element-x は
   **再記録を maintainer がラベルを付けた CI ジョブでのみ**実行し、**手元で黙って
   上書きする道を運用から外している**
3. **検査そのものが動いているかを、別の機械で見る。**
   - `muter`（563★）… Swift に変異を注入し、テストが気づくかを測る
   - RevenueCat … **新規ファイルが .xcodeproj に入っていない**（＝テストが静かに
     実行されない事故）を Danger で検出
   - Signal … **pre-commit と同じ検査を CI 側でも回し、`--no-verify` を無効化**

### 私の案

`layout_check` を必須段にし、走れなければ 2 を返し、`まだ測れない` の宣言でしか通さない。

### 採るほうと理由

**私の案は残しますが、それだけでは足りません。**先人から2つ足します。

- **`--no-verify` を無効化する。** Signal の形です。**PlantTalk では1日で3回使われました。**
  pre-push で止めても、同じ検査が CI に無ければ意味がありません。
  **我々の CI は案件によって段が違います**（FlashEnglish は7段が CI だけ）。
  **pre-push を飛ばした push を CI が受け止めるか**を確かめる必要があります
- **正解の更新経路を閉じる。** golden やスナップショットの取り直しが**手元でできてしまいます。**
  element-x のように「再記録はラベル付きの CI ジョブだけ」にすると、
  **黙って正解を書き換える道が無くなります**

**`muter`（変異テスト）は、我々が手でやっている仕込みを機械化したものです。**
我々は段ごとに手で仕込んでいますが、muter は自動で当てます。**取り込む価値があります。
確信度 中**（Swift 6 での動作は未確認）。

## 論点1: スタックを移すときの手順

### 先人がやっていること

**「このプラットフォームには無い」を機械が検証できる形で持っているのは、14件中1件だけでした。**

- **adobe/spectrum-design-data**（154★）… manifest に `modeSetRestrictions`
  （例「iOS は light のみで dark を持たない」）を宣言し、**検証ルール SPEC-041 が
  「制限の結果どの候補も解決できない」をエラーにする**。
  移行の手順書 `PLATFORM_EXTENSIONS.md`（命名規約・必須フィールド・配置先・
  validate→test→changeset→PR）も持つ

  区別されません**

そのほかに繰り返し出てきた形が2つあります。

| 形 | 例 |
|---|---|
| **共有層と専用層をディレクトリで分ける** | Skyscanner: `common/base`（全部）/ `common/app`（iOS と Android のみ）/ `-web` `-android`（専用）。**どこに置くかを決める時点で「これは全部に要るのか」を1回考えることになります** |
| **未対応を「表の ❌ 行」として残す** | DB UX（Next.js を ❌ で表に残す）、material-color-utilities（言語別の可用性表）、OUDS の wiki（未実装は版情報が空の行）、Gestalt（`notAvailable / partial / planned / ready` の型） |

**そして、仕組みがあっても片肺になる実例が2つ見つかりました。**

- **Gestalt** は型まで持っているのに、**対象が `figma` と `web` のみ**で iOS/Android は
  宣言の対象から外れています
- **OUDS** は iOS に一覧の wiki があるのに、**Android には同等のものがありません**

**そして、いちばん重要な発見がこれです。**

> **「新しいプラットフォームを足すときの手順書」は、15件のどこにも見つかりませんでした。**

あるのは「新しい**コンポーネント**を足す手順」（OUDS Web の create-component、OUDS iOS の
issue テンプレート）、「新しい**出力形式**を足す手順」（primer の build-system.md）、
「新しい**ブランド**を足す手順」（Mística の adding-new-brands.md）だけです。

**プラットフォーム追加が「めったに起きないので手順化されない」のか「手順化できていない
だけ」なのかは、この調査からは判断できません（未検証）。**

**我々に直接刺さる実例が2つ出ました。**

- **Decathlon Vitamin** … 中央の `vitamin-design` は動いているのに、`vitamin-ios` は 2024-05、
  `vitamin-android` は 2023-10 で止まっています。**中央だけが生き残り、各プラットフォームが
  先に止まった実例**です
- **Telefónica Mística** … 新しいトークンが web 側に取り込まれていなければ CI が PR を
  落とします（`check-token-import.js`）。**ただし検査するのは web だけで、iOS と Android には
  同じ検査がありません。**「片方だけ守られている」状態がそのまま残っています

**我々も同じ形です。**Flutter の2案件には検査があり、Swift の案件にはこれからです。
**片肺になる**というのは、我々に起きつつあることです。

**つまり論点1は、先人から手順は取れません。取れるのは「表を持つ」という形だけです。**

### 私の案

### 採るほうと理由

**方向は合っていましたが、やり方を変えます。**

    design/deliverables.json
      行: トークン層 / カタログ / 対応表 / 照合テスト / 生成器 …
