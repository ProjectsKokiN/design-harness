# 本番リリースの合格条件（production gate）

**本番モードの案件が、Web の公開・アプリの iOS / Android ビルドに進んでよいかを
機械で判定する条件。** ここが「Figma と完璧に合っている」の定義の正本になる
（2026-08-28 ユーザー方針。散文の言い換えを作らず、この表を参照する）。

制作モードの分岐（プロトタイプか本番か）は `~/.claude/CLAUDE.md` の
「制作モードの分岐」が正本。ここは本番モードに入ったあとの合格条件だけを持つ。

## 前提

- 判定はすべて機械。**画像の見比べは条件に含めない**（見た目の評価はデザイナー本人が
  リリース判断の外で行う。機械の合格は「Figma の指定どおり」の保証であって
  「美しい」の保証ではない）
- 条件は**全部**満たす。1つでも欠けたらリリースに進まず、欠けた項目を報告する
- 各条件は「仕込みで落ちること」を確認済みの検査で見る（通ることの確認だけでは
  何も見ていない可能性を排除できない）

## 合格条件（6つ）

| # | 条件 | 何で測るか | 落ちたときの意味 |
|---|---|---|---|
| 1 | 禁止パターン 0・静的解析 0・テスト全通過 | `design/verify.sh`（統合入口） | 制約層の違反が残っている |
| 4 | **鮮度** — 書き出しが Figma の現状と一致 | **`design/` を触る機体でだけ必須**（`machine_scope.py --owns design/` が段を結ぶ）。担当機ではトークンが無ければ落とす。担当外の機体は機体名と理由を出して飛ばし、`--check` が「担当外のパスを変えていないか」で穴を塞ぐ | 書き出しは撮った瞬間の写し。Figma が直されていれば全照合の前提が崩れている。**ただしこの失敗を起こせるのは `design/` を触る機体だけ** |
| 5 | **再現性の判定に穴が無い** — Figma の全セットにスタック再現性の判定（○△×）があり、× は 0（または全 × に人間の判断記録がある） | `tools/check_render_gaps.py`（網羅検査つき） | 値が一致しても描画で別物になる指定が残っている（負の spread で影が消える等） |
| 7 | **実装網羅 100%** — Figma にあるコンポーネント・トークン・スタイルが**すべて実装されている** | `impl_coverage_check.py`（未実装が1件でもあれば落ちる） | AI が「使わないから作らない」を独断で決めている |
| 8 | **検査が生きている** — ルールが実際に発火することを種で確認済み、かつ「見なかったもの」が機械の出力である | `seed_check.py`（ルールごとの発火件数が宣言どおり）＋ `gen_rules.py --check`（段の値が tokens と一致）＋ `gap_report.py`（走査が空振りなら落ちる） | **違反 0 件と、そもそも見ていないのは、出力上まったく同じに見える。** aub の幽霊ルールは一度も走らないまま緑だった。`check_flutter_gaps.py`（現 `tools/check_render_gaps.py`）は26セット中10セット未評価のまま「× 0件 / exit 0」を返した |
| 9 | **見本と相互作用** — 値ではなく「形」と「数」。重なり順・見本に渡す子の数・軸の作り方・状態の駆動が Figma と一致 | `tree_test_check.py`（状態・スロットを持つセットを分母にした網羅）＋ 案件の widget test。**描画は見ない**（木と数だけ） | **値の検査は全部通るので、AI からは気づけない。** aub の実害: 内側の影が文字とアイコンを覆った／背景ぼかしの切り抜きが落ちる影を消した |

**番号が飛んでいるのは廃止したためです**（3 と 6 は記録層とともに 2026-08-29 に廃止。
**2 は 2026-09-03 に廃止**——下の節を読むこと）。
**抜けではありません。** 条件は**全部**満たします。

### 条件2「照合相手は書き出しだけ」を廃止した（2026-09-03 ユーザー確定）

> 条件2は廃止で

**この条件はもう関門に入れません。** リリース判定で数えるのは 1・4・5・7・8・9 の6つです。

**廃止しても、条件2が守ろうとしていた失敗は消えていません。** 記録として残します。

- 何が危ないままか: **AI が手で書いた期待値は、自分の答案の自己採点になる。**
  aub で「検査は緑なのに Figma と違う」誤り8件は、全部が手書きの層から出ました
  （機械生成の層は 0 件）
- どこに残っているか: 既存案件の `design/values/` のうち**手書きのもの**。
  FlashEnglish の実測（2026-09-03）では `layout.json` 116件・`autolayout.json` 4件が
  手書きで、ほかは生成物でした
- **新しく手書きの照合相手を作らない**、という方針自体は残します。廃止したのは
  「関門で機械的に落とす」ところだけです

廃止に伴い、条件2のためだけに置いていた検査
（`gen_input_check.py` / `expectation_source_check.py` / `exporter_check.py` /
`coverage_check.py`）は**関門の段から外します**。道具としては残すので、
移行を進める案件は手で回せます。

**2026-09-02 に条件9 を表へ足しました。** それまで条件9 は本文（下の「条件9 の測り方」）に
定義があるのに**表に行がありませんでした**。表を見て判定すると条件9 が抜けます。
条件9 は「値の検査が全部通るので AI からは気づけない」性質のものなので、
**表から漏れているのが最も危ない条件**でした（414 セッションの指摘・2026-09-02）。

### 条件7について（2026-08-29 ユーザー確定・ハーネス全体の規則）

> **Figma にあるコンポーネントは文字どおり全部実装する。Variables に登録されている
> トークン、スタイルもすべて完璧に実装する。機械的に行い、AI がどれを作る・作らないを
> 判断しない。**

これは既存の規則「**Figma に無い値は生成しない**」「勝手な視覚的発明をしない」と
**対になる**規則。それまで片方（無いものを作らない）しか無かったため、
**AI が「このアプリでは使わないから作らない」を独断で決められる状態**が残っていた。

- **デザインシステム単位で判断しない。** 「この案件では使わない」は理由にならない。
  使わない部品があるなら、消すのは Figma 側であって実装側ではない
  （その判断はデザイナーが Figma で行い、書き出しに反映されて分母が下がる）
- **除外の宣言で分母を縮めない。** `catalog-exceptions.json` の `notShown` は
  「見本に出さない」ための宣言であって、**実装しない理由には使えない**
- 書き出しの `$meta.excluded` は、**Figma から機械的に読めないもの**にだけ使う
  （実例: 414 の `Icons` は 456 バリアントのアイコン一覧で、字形はフォントが持つため
  寸法・色の照合に使う情報が無い）。「使わないから」で足さない

### 記録層の廃止（2026-08-29 ユーザー確定）

> 実装と記録を見比べる必要はないです。実装と Figma を見比べればいいです。

**手で書く記録層（`design/values/`）は廃止した。** 照合相手は Figma の機械書き出し
（`figma/*.json`）だけ。実務上の「実装 ↔ Figma」は「実装 ↔ 書き出し（リポジトリ内の
JSON）」で、書き出しの鮮度は条件4が担保する。**この2段を
混同しない。**

- 根拠（aub の実測）: 記録層 479 件のうち **477 件は Figma が機械で答えられる値**
  だった。手で書き写したことで 8 件まちがえ、機械生成の層の誤りは 0 件だった
- 旧条件3（pending 0）と旧条件6（記録が語彙どおり）は**記録層とともに廃止**。
  新規案件には適用しない（記録層を作らないため）。既存案件では移行が終わるまで
  従来どおり測る
- 記録層に残してよいのは **Figma に無い値の申告だけ**（`design/figma/missing.json`・
  `templates/figma-missing.json.template`）。これは記録ではなく**例外の宣言**
- 経緯のメモ（旧記録の `note`）の行き先は、コード・テストのコメント／DECISIONS.md／
  コミットメッセージ。「なぜこの値か」「前回どう間違えたか」が読めなくなると同じ誤りが戻る
- **画面固有の値の照合先は `figma/frames.json`**（画面のノード木の機械書き出し）。
  これが無い案件は記録層を消せない（廃止の前提条件）。

  **この前提条件は `tools/screen_export_check.py` が測る**（2026-09-04・#14）。
  それまで散文だけで、機械で確かめる段がなかった。**「在る」と「足りている」は
  違う。** FlashEnglish は `frames.json` を持っていたので前提条件を満たして
  いるように見えたが、中身は3件の「部品にならない枠」で、画面のノード木では
  なかった。結果、手書きの記録層 63 件のうち置き換えられるのは 9 件だけで、
  **残り 54 件は照合先が存在しなかった。** この決定は画面の値については
  5日間**実行不可能**なまま、誰も気づいていなかった。

  書き出し器は `design-harness/exporters/export_frames.js`（2026-09-04 に
  aub-familywalk から回収）。案件ごとに書き換えるのはページ名・節・版面の幅だけ。
- 生の木を照合が毎回読むことで、**AI の「翻訳」（`counterAxisAlignItems: MAX` を
  "bottom" と書き写す等）が「正」になる余地を消す**。アルバムの開始とゴールの
  上下逆はこの翻訳で起きた

### 既存案件の移行（2026-08-29 ユーザー確定）

**FlashEnglish / planttalk / qnd-database の移行は、ユーザーがその案件を再開する
ときに確認する。** それまで `coverage_check.py` は `fail_on_values: false`（猶予）で
走らせるが、**残数（記録ファイル数）を毎回表示する**。猶予を無期限の宣言にしない
（aub の `_pending.json` が 169 件溜まった前例）。

## 完了報告の書式（2026-08-29 新設）

**できたことより先に、残っている最大の限界を書く。** aub で「照合の穴 0」を見出しに
して、31 部品中 9 部品しか実装していない事実を表の中に埋めたまま、他マシンへ実機確認を
依頼した実害から。

```
## 残っている最大の限界
[未実装 N 件 / 未検証の項目 / 猶予中の残数。無ければ「なし」と書く]

## 合格条件の現在地
[条件ごとに数字。「概ね良好」と書かない]

## できたこと
[...]
```

新設した検査がある場合は、**壊して落ちた出力**をレポートに含める（「通ること」の
確認は何も証明しない。aub のカタログ描画検査は、節を丸ごと消しても素通りした）。

## 適用時期

- **新規案件**: 最初から全条件を課す
- **既存案件**（FlashEnglish・aub-familywalk 等）: 次のリリースまでに段階的に満たす。
  それまでのリリース判断は、残数（条件5・7 と移行猶予の記録ファイル数）を明記した報告を添えて
  ユーザーが行う。**残数を書かずに「検証済み」と報告しない**

## プロトタイプからの昇格

プロトタイプとして作ったものを本番に上げるときの手順（2026-08-28 ユーザー確定）。

1. **視覚に関わる値・スタイルをすべて削除する。** 色・寸法・余白・角丸・タイポ・影の
   直書きと、プロトタイプ用に適当に決めたトークンを全部消す。コードの骨格・ロジック・
   画面遷移は残してよい
2. `/mobile-harness-setup` を通常どおり実行し、**Figma を正として**トークン・生成物を
   作り直す
3. **「いまのコードを正解データにする」手順（figma-fullexport.md の既存プロジェクト向け
   手順）は使わない。** あれは本番として書かれたコードにだけ適用する。プロトタイプに
   適用すると、適当に決めた値が正解として固定される
4. 以後は本番モードの通常フロー（/mobile-implement-ui ＋ この合格条件）

## 検査の実装はどこにあるか

検査エンジン・鮮度差検査・語彙・ラチェットの正本は
**design-harness リポジトリ**（https://github.com/ProjectsKokiN/design-harness）。
案件には submodule（design/harness/）とシムだけを置く。仕組みの改善は
design-harness に入れると全案件へ届く（`git -C design/harness pull`）。

## 関門はどこで走るか

- **CI（push 時）が関門。** hook（保存時）は即時フィードバックの補助であって関門ではない。
  hook はプロジェクト外の cwd から作業すると読み込まれず、Bash 経由の編集にも
  発火しないことが実測で分かっている（2026-08-28 aub-familywalk。禁止パターン違反7件が
  hook を素通りした）。QnD が先にこの結論に達している
  （qnd-database の harness/README:「保存時の hook は書き込みを止められません。
  実際の関門は push 時の CI です」）
- CI が無い段階の案件は、`git config core.hooksPath` の pre-push から `verify.sh` を呼ぶ
  （FlashEnglish 方式）。それも無い最小構成では、リリース前に人が `verify.sh` を
  1回叩くことが関門になる——この状態は「本番モードの整備が未了」として扱う

## 条件4（鮮度）を、責任のある機体に結び直した（2026-08-30 ユーザー確定）

`verify.sh` は push 前に**全マシンで**走る。そこに「`FIGMA_TOKEN` が無ければ落とす」を
置いていたため、**Windows**（トークンが `.env` に無い）と **Mac mini**（HTTP 403）が
この段だけで止まっていた。両方ともユーザーにしか直せない状態だった。

**しかしこの段が守るのは「Figma を変えたのに書き出しを取り直していない」状態**で、
それを起こせるのは `design/` を触る機体だけ。Windows と Mac mini は `design/` を
触らない（正本: `machine-relay/references/worker.md`）。つまりこの2台は
**自分には起こせない失敗を確かめるために**トークンを求められていた。

### 3つの規律

| | |
|---|---|
| 担当の機体 | **必須のまま。** トークンが無ければ落とす（そこで落ちなければ意味がない） |
| 担当外の機体 | **機体名と理由を出力に残して飛ばす。** 黙って飛ばさない |
| 対の検査 | `--check` が、担当外と宣言した機体が担当外のパスを変えていないかを見る。**飛ばした穴をここで塞ぐ** |

**段を減らしたのではない。責任のある機体に結び直した。**
（2026-08-29 に一度「必須段から外す」としたが、2026-08-30 にこの形へ改めた。
外すと、担当機でも回らなくなる——planttalk は実際に「トークンが無ければ飛ばす」に
なっており、**トークンを読み忘れた担当機でも検査が消えていた**）

### 宣言

担当は案件ごとに変わりうるので `design/machine-scope.json` に置く。
**`verify.sh` に機体名を直接書かない。**

機体の判定は `machine-relay/SKILL.md` の Step 1 と同じ方法（`scutil --get ComputerName`）。
**判定できなければ飛ばさず落とす**——知らない機体を素通りさせると、
「担当外だから飛ばした」で全段が消える。

`staleness_check.py`（**書き出し → 生成物**）はネットワーク不要で、
**どの機体でも必須のまま**。別物なので混同しない。

## 条件8（検査が生きている）の測り方（2026-08-29 新設）

**この条件だけ、検査そのものを検査します。** 他の7条件は実装を見ますが、
8は「その7条件の検査が働いているか」を見ます。

### 3つの道具の担当

| 道具 | 数えるもの | 捕まえる失敗 | 実害 |
|---|---|---|---|
| `attack/engine_attack_test.py` | エンジンの挙動 | エンジンが壊れた | — |
| `expected_targets`（rules.json） | 読んだファイル数 | 対象が黙って狭まった | QnD 2026-08-28: 除外1語で19ファイル減っても緑 |
| **`seed_check.py`** | **ルールごとの発火件数** | **ルールが黙って死んだ** | aub: `require-semantics-on-tappable` が実装の無いまま一度も走らなかった |

**ファイルは全部読んでいるのに、ルールが1件も当たらない**——これは上2つを素通りします。

### 種（seed）の置き方

    design/seeds/
      seed_<rule-id>.dart      # そのルールの違反を意図的に1件書く
      expected.json            # {"<rule-id>": 1, ...}

**種は2つの経路から外してください**（片方だけだと落ちます）。

1. `rules.json` の `exclude_paths` に `design/seeds/`
   （通常の走査に混ぜると、意図した違反が本物として報告される）
2. **静的解析の除外**（Flutter は `analysis_options.yaml` の `analyzer: exclude:`、
   Web は tsconfig / eslint）。**2 を忘れると `flutter analyze` が種を解析して
   落ちます**（2026-08-30 に FlashEnglish で実際に踏んだ。`Undefined name 'Sem'` が5件）

ひな形は `design-harness/seeds/<stack>/` と `<DS>/seeds/<stack>/` にあります。
両方を案件の `design/seeds/` へコピーし、`expected.json` を合成します。
**`"*": true` にすると「rules に載っている全ルールに種が要る」**という宣言になります
（段階導入の途中は外し、全ルールに種が付いたら真にします）。

### 段の値が入るルールは生成物

`no-offscale-radius` の正規表現には角丸のスケールが手で埋め込まれていました
（2026-08-29 時点では 414 の CornerRadius と一致していましたが、Figma で段を変えた
瞬間に静かに古くなる）。**`gen_rules.py` が tokens.json から生成**し、
`--check` で「tokens を取り直したのに生成し直していない」を検出します。

### 見なかったものは機械が出す

完了レポートの「残っている限界」は `gap_report.py` の出力をそのまま貼ります。
**AI が自分の言葉で書き直しません。** 書き落とせば報告書は合格したように読めます。

## 条件9（見本と相互作用）の測り方（2026-08-29 新設・aub-familywalk の反省録より）

**この条件だけ、値ではなく「形」と「数」を見ます。** 値がすべて Figma と一致していても、
重なり順・子の数・軸の作り方・状態の駆動が違うと画面は別物になります。
そして**値の検査は全部通る**ので、AI からは気づけません。

**描画（レンダリング結果）は見ません。** ウィジェットの木と数だけで判定します。

### 9-1. 効果と子の重なり順（木の構造で分かる）

Figma の効果（内側の影・ぼかし・線）は**節点の塗りに掛かり、子はその上**に描かれます。

- 効果を描く要素が、文字・アイコンの**祖先かつ前面**になっていないこと
- 切り抜き（`ClipRRect` 等）が、**落ちる影を持つ箱を囲っていない**こと

aub の実害: 内側の影が文字とアイコンを覆った／背景ぼかしの切り抜きが落ちる影を消した。
どちらも `foregroundPainter` と `ClipRRect` の位置の問題で、**木を見れば分かります**。

### 9-2. 見本に渡す子の数（数で分かる）

- `vis: true` のスロットが実装に届いているか
- 見本に並べる子の数が書き出しと一致するか

aub の実害: Footer の見本が `SlotTop` だけで高さ 148 が 88 になった。
Chips・ButtonsGroup・BottomNavigation・EmptyStates・Tabs で子の数が書き出しと違った。
**「使わないから出さない」を記憶に明文化していても5回破りました**（条件7の再発）。
**文章の決まりでは守れません。数で照合してください。**

### 9-3. 軸は実タプルから作る（掛け算の禁止）

バリアントの組み合わせは、**書き出した実タプルだけを正**とします。
軸の値を掛け合わせて作らせません。

aub の実測: Images 8 → 16、Chips 35 → 70。`State` が2つの軸群に現れる／
従属軸を独立に掛けた結果、**Figma に存在しない組み合わせ**が見本に並びました。

### 9-4. 相互作用が駆動されているか

書き出しに `Hovered` / `Pressed` があるなら、**部品がポインタを見て実際に切り替わる**
ことを、ウィジェットの木と状態遷移で確かめます（木の中の面の色が変わるかを見ます）。

aub の実害: 8セットぶんの状態が Figma にあるのに、駆動するものがゼロでした。
**「描ける」で完成と見なしていた**ため、バリアント網羅の検査は通っていました。

**台帳（`generators.json`）を持っていたのは1件だけ**で、残りは一覧が

### 台帳が唯一の正

## 課題は Issue に集める（2026-09-02 ユーザー確定・運用の流れ）

> 各プロジェクトでハーネスの仕組みを使用して開発を行っていって、課題が発見されたら、
> イシューの中にためていくようにしたいです。定期的にあなたに連絡するので、
> あなたはその課題を網羅的に解決して、判別の仕組みを改善していくというふうな流れになります

```
案件がハーネスで開発する
  → 課題が見つかる
  → **宣言する**（why と期限を書く）
  → Issue に立てる（issue_sync.py --apply）
  → **定期的に共有層のセッションがまとめて解く**（issue_sync.py --inbox）
  → 直したら宣言を消す → Issue が閉じる
```

### 課題が見つかったときにやること

**1. 宣言する場所があるなら、そこに書く。** 宣言の場所と語彙:

| 何が起きたか | 書く場所 | 語彙 |
|---|---|---|
| 関門を段階導入で外している | 該当の設定 | `$warn_only`（文字列。理由と外す条件） |
| この項目だけ検査から外す | `allow` / `allow_tokens` | `{name, why, reviewBy}` |
| 数値で検証できない | `gaps.json` の `notVerifiable` | `{name, why, reviewBy}` |
| Figma に値が無い・書体を代用した | `missing.json` / `font-substitutions.json` | `{id, reason, expires, decidedBy}` |
| **直す場所が共有層にある** | 案件の `remaining.json` | `{id, what, why, how, blockedBy, issue}` |

**2. 宣言する場所が無いなら、Issue を直接立てる。**

```bash
python3 design/harness/tools/issue_sync.py --new \
  --title "…" --why "…" --closes-when "…"
```

**`--closes-when`（何が分かれば閉じられるか）は必須です。** それを書かない課題は、
開いたまま忘れられます。

**3. `FINDING-*.md` のようなその場限りのファイルを作らない**（2026-08-30 に作って
しまった実例があります）。リポジトリを開かないと見えず、誰も棚卸ししません。

### 課題と「期限つきの決定」を分ける

**期限で自動的に分けます。** 期限が遠い宣言は「いまは決着している」、
30日以内に近づいたら「やること」。**手で印を付けないので、印の付け忘れが起きません。**

実測（2026-09-02）: 宣言67件のうち、いま課題とするものは7件。

### どのリポジトリの Issue にするか

**`blockedBy` で決まります。** 案件で見つかっても直す場所が共有層なら、
Issue は共有層（design-harness）に立ちます。立てた URL は宣言に書き戻すので、
同じ課題が二重に立ちません。

### 関門

`verify.sh` と CI に「**Issue の無い課題**」の段があります（`issue_sync.py --check`。
網に触りません）。**宣言したのに Issue にしていない状態で通りません。**

**CI からは Issue を作りません。** 通るたびに増えて誰も読まなくなるためです。
作るのは人（またはセッション）が `--apply` を回したときだけです。
